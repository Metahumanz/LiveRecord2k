## 已证实的主因：SSE 写缓冲恢复循环

`src/server/app/state-publisher.cjs` 的 `pauseClient()` 在每次 `drain` 后无条件执行 `writeState()`。`response.write()` 返回 false 代表数据已接收、暂时不要继续写，不代表这一份快照发送失败。

当前一个 SSE 客户端的整份状态约 **290594 字节**，响应的 `writableHighWaterMark` 是 **65536 字节**。一份快照天然超过阈值，每次发送都会返回 false：

1. 发送整份状态，进入暂停并等待 drain。
2. 缓冲排空，恢复回调再次发送整份状态。
3. 新快照再次超过阈值，继续等待 drain，重复循环。

两次 3 秒真实 CPU 采样的主要热点均为 `StatePublisher.formatEvent()` 的 JSON 序列化和 socket 写入。暂停采集到的栈包含 `writeEvent → writeState → resume → socketOnDrain → afterWriteTick → processTicksAndRejections`，和上述循环完全对应。

独立本地真实 HTTP 复现使用相同 64 KiB 阈值、约 291 KB 状态，在 **零次状态变化** 下连续写出 8 份完整状态、接收 2324680 字节；复现工具在第 8 次主动结束，避免无限循环。不是只根据静态源码猜测。

这个循环持续占用事件循环，拖延 HTTP 响应、B站请求回调、子进程输出读取、超时处理以及 I420 管线的数据转发。保留的 400 条应用日志中有 291 条 B站 15 秒超时；同时出现 FFprobe、媒体时间轴扫描和更新检查超时。不能把这些超时都当成独立网络故障。

SSE 相关代码的 blame 指向 9 月 9 日的 `74a1275a`，昨天的修复没有修改该文件。昨天隔离烧录工具不调用服务 init，也没有浏览器 SSE 订阅，因此通过样片和安装后 helper 验收并未覆盖这个长期运行触发条件。

## CPU 兼容链及诊断缺口

10:12:38 的真实源预检通过，报告原生 NVMM 约 162 fps，但 10:13 开始的正式任务日志已经是 CPU Scene/I420 链路。正式服务的 CPU/子进程和快照也证明当前确实在使用该链路。

代码存在两个相关问题：

- `runChunkedJetsonSceneGraphExport()` 预检通过后，把 `chunkSeconds` 设成整项任务时长。若正式原生运行在早期失败后回退，当前段仍沿用整项时长；没有重新应用 CPU 兼容路径的 20 秒段上限。
- 回退原因传给 `onStderr()`，但导出的该回调只记录含英文 `error|failed|invalid` 的行。诸如“媒体信息探测超时”“PTS bridge 未通过”等纯中文错误可能丢失。其他失败通过 `compactLogLine()` 截断后，日志往往只剩开头的 libass/Argus 提示，真正的末尾失败原因没有保留。

昨天新增的帧率回退逻辑在正式原生运行前还会再次探测源信息。主线程阻塞导致该探测超时，并进入早期兼容回退，是与当前日志及代码路径一致的解释；**当前任务的准确首次异常未完整记录，不能把这项推断当成已经捕获的运行时错误**。

独立进程探测当前同一源文件只需 **0.02286 秒**，成功读到 2560×1440 HEVC、`r_frame_rate=60/1`、视频首 PTS 1.019 秒、容器时长 160.018 秒。这排除了“当前源文件本身无法探测”这一解释，但不能否定共享盘此前的瞬时异常。

## 其他已发现的问题和边界

- 主机 `/tmp/argus_socket` 存在，正式服务私有临时目录中不存在；systemd 的 `PrivateTmp=true` 隐藏了这个 socket。这解释反复出现的 `Connecting to nvargus-daemon failed`。同类警告在成功任务中也存在，它本身不足以证明 NVDEC/NVENC 失败，更不能据此将所有故障归因到摄像头服务。
- 05:47:55 内核确实报告了一次 SMB 签名验证失败（`-13`）。它是独立的共享盘异常证据，与本次 SSE 主线程阻塞不能混为一谈；未修改挂载和 SMB 安全配置。
- 未带账号凭据的独立 B站公开请求在 0.188 秒内返回 HTTP 412。网络能够收到响应，但这不是完整登录请求的成功证明，也不能排除 B站风控或另一类网络错误。
- 日志中 06:13–10:12 的 3600 秒导出历时约四小时，原生链路末报告约 160.89 fps、216000 帧且内部 PTS 映射通过。内部管线速率和任务实际耗时不能混用；这些记录符合主线程/管线调度被拖慢的现象。
- Orin 正式导出的成功条件仍主要是视频流与文件大小检查；昨天的真实字形抽帧验收在独立 CLI 中。日志中的“已导出”不能单独证明全部弹幕或原片绝对音画同步正确。

## 用户新增日志中的失败与修复

1. **真实 MP4 编辑列表**：短片首帧实际为 1.029 秒，但 qtdemux 传出的压缩 PTS 为 0.033 秒，空编辑时长位于 SEGMENT.base/time。只改 NVMM buffer 的 Python PTS 不能修复其底层元数据。现在先读取容器空编辑，物化必要黑帧，并在 NVDEC 之前将压缩 PTS/DTS 转成运行时间、转发零基准 SEGMENT；不从陈旧 sidecar 或单纯 A/V 首 PTS 差猜测黑帧。空编辑已属于采集弹幕时钟，不能再把它重复加到 Scene 事件上。
2. **编码器帧率**：容器平均帧率 60.0017 和 NVMM caps 中的 0/1 均不能充当编码时钟。原生管线采用源 60/1，在 NVENC 前通过 capssetter 明确帧率；合并规范化也将很小的平均帧率误差归回源有理数帧率。修复前的 HEVC 帧率头错误会造成解码后的成片时间戳倒退；新测试检查真实解码帧，不以内部 PTS 配对通过代替成片验证。
3. **取消无效**：原生 helper 没有传出子进程句柄。现在真实源预检、纹理准备和正式渲染都传递 onChild，取消不触发兼容重跑；队列等待与准备期间的取消标记也保留到任务启动检查。helper 临时纹理放入所属导出工作区，强制结束后由父任务清理。
4. **临时盘满**：8759.9 秒任务真实报 `No space left on the resource`，不是显存不足。共享盘虽然剩余约 1.5 TiB，原生中间文件实际写在仅剩约 32 GiB 的本地系统盘。现在渲染前检查本地中间文件与封装输出的空间，并保留安全余量；不允许处理数小时后才发现磁盘不足。
5. **共享盘发布**：另一条 3156.97 秒任务在 MP4 最终关闭时出现 `Permission denied`，内核此前另有 SMB 签名验证失败证据。当前正式 UID 996 的新临时文件写入、seek、fsync、关闭、重开和改名测试通过，无法据此认定历史瞬时错误消失。共享盘目的地现在先在本地封装并验证，再流式复制到目标同目录唯一临时文件，完成后原子改名；复制失败不移走原成片，并保留已验证本地成片。没有更改 SMB 验证或放宽挂载权限。
6. **合并与重试**：取消标记残留、重试选择错误组、已存在但损坏的输出遮挡重试，均已修复。源列表新增“手动选择合并”，仅合并同一房间已完成录像，按录制时间排序；完整时长录像也可手动选入，所有源文件和库记录保留。自动合并仍遵守原有分段边界。
7. **成片准入**：正式 Orin 导出先在有可见文字的位置生成最多 10 秒样片，检查实际文字边缘。缺字形直接停止并保留样片和诊断。过期 ass-compat-v2 报告不能获得准入，已更新为 v3；不为未使用的兼容路径预建整片滤镜。
8. **正式环境的自动挂载识别**：`/mnt/zzzz` 同时出现 autofs 与 CIFS 挂载记录，旧逻辑按最长路径选择时取到 autofs，误判为本地文件系统，使上千个纹理临时文件写入共享盘，准备阶段明显变慢。现在同路径优先实际文件系统，尚未解析的 autofs 保守按非 POSIX 目的地处理。正式服务重新验收已确认本地工作区和共享盘发布正常；没有修改挂载权限或 SMB 验证设置。
