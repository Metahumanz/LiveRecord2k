# Windows NVIDIA 长录像烧录回归修复

2026-09-26，在 `dev` 修复，以 `main@021e1f1` 为对照。原始录像、弹幕 JSONL、Scene 缓存均只读保留；测试成片和诊断写入本机 `.tmp/desktop-burn-regression/`。

## 原因与证据

1. **NVENC 被误当成 CUDA 合成准入。** 桌面视觉门禁未通过时，备用 Scene 路径仍根据编码器名字选择 `target: cuda`，并提前构建未使用的大滤镜图。现在按桌面策略选择实际路径，按需生成脚本；桌面与 Jetson 的导出调度分开。
2. **对象数放大为长时间输入流。** 同一份 8759.91 秒录像有 9283 条事件、9419 个 Scene 对象。基线生成约 7.92 MB 滤镜脚本、10059 次 CUDA 上传和 9440 条贯穿整片的输入流。修复后按整数帧分为 438 段，每段最多 20 秒，实际最多 88 个对象；配置上限为 128 个滤镜层。纹理流只存在于对象生命周期内。此项对照只构建脚本，没有重跑危险的旧整片任务。
3. **透明纹理没有字形 alpha。** 旧 CUDA ASS 纹理缺少 `alpha=1`。真实 FFmpeg RGBA 回归证明，默认 ASS 渲染后的字形 alpha 全为零，合成时完全不可见；修复后存在可见字形。这是“编码成功但没有弹幕”的直接原因之一。
4. **旧 Scene 缓存写入了字面 `\\n`。** 原缓存不能按 JSONL 正常解析。现在写真实换行，并兼容读取旧缓存；原 JSONL 非空时优先采用原事件，记录缓存数量不一致。没有重写原缓存。
5. **硬解失败后可能整片重跑。** 原有宽泛 CUDA 错误判断覆盖了显存不足、滤镜图资源不足和晚期失败。现在只允许明确的解码兼容错误在媒体处理不超过 5 秒、启动耗时不超过 30 秒时重试 CPU 一次。记录错误类型、当前尝试处理时间和整项任务完成的媒体时长；资源不足及晚期失败直接停止。
6. **视频首帧晚于音频，分段时可能移动画面。** 真实录像第一帧视频 PTS 为 1.014 秒。重置首帧时钟会使首段多读，并与下一段重叠。现在保留缺少视频的前导区间，按 CFR 帧边界合并；音频整条一次封装，避免每段 AAC 编码带来的累计偏移。
7. **带前导的 ASS 金标准重复加时间偏移。** 原参考滤镜先把源 PTS 加前导，再让 concat 加一次前导，导致真实 CUDA 门禁出现整帧差异。现在在 ASS 按录像时钟渲染后、进入 concat 前复位源 PTS。重跑六组真实硬件对照全部通过，普通与 1.019 秒前导均覆盖。

## 当前策略与验收

- `h5-card`、`bubble`、`minimal` 使用已有 ASS 兼容合成，保留 NVENC 硬编码。
- 其他 Scene 样式使用有上限的桌面分段合成。无缩放的大字号纯文字段直接在 YUV 视频上绘制字形，减少透明输入流和全帧 RGBA 转换；小字号、缩放及卡片保留原纹理路径。
- 桌面软件合成同时占用 CPU 与编码器调度预算，防止 NVENC 名称掩盖 CPU 合成开销；保留录制优先的资源约束。
- NVENC 可用不代表 CUDA Scene 合成可用。视觉报告必须匹配实际环境指纹、渲染器版本并在 7 天内；无时间、无指纹、未来异常时间或过期报告均拒绝。现阶段即使旧样式门禁通过，也继续采用 ASS 兼容路径。
- 正式任务前先编码实际有字形的 10 秒样本，以原纹理渲染器作为独立参考；与只去掉文字的控制帧比较字形边缘。没有预期弹幕立即报错并保留诊断。正式成片再次抽帧验收。
- 逐段检查实际输出时长及时间戳，合并后检查全流连续性。编码器返回成功不等于验收成功。
- Windows FFmpeg 使用明确的系统/用户字体目录与可写缓存。中文和符号渲染已检查；使用缺少中文字形的 Segoe UI Symbol 主字体，实际验证 libass 能找到中文回退字体。
- Windows 自动烧录时长达到 300 秒的录像暂时暂停；手动导出和回归脚本仍可用于验收。**此策略仅在修复版启动后生效，不会停止另一台机器仍运行的旧进程。**

有效 fps 包含预检、探测、编码、封装及验收的总耗时。内存是每 1.5 秒采样的 FFmpeg Working Set；GPU 指标是整张显卡总占用，包含其他程序，不能解释为本任务独占显存峰值。YUV 任务总显存采样峰值分别为 7550/7607 MiB，Node RSS 峰值为 126.0/129.3 MiB；这一轮本机有明显的其他 GPU 占用，因此不能据此判断 5060 Ti 的空闲设备性能。5 分钟耗时相对本轮 RGBA 路径下降约 37.7%，仍不能认定 Ti 性能已恢复到旧可用版本水平。

自动化验证：快速测试 30 个文件、集成测试 9 个文件、包契约测试 3 个文件全部通过。新增桌面回归覆盖 18 项，包括无字形成片拒绝、预检失败不启动正式长任务、最终成片失字拒绝、两小时万条事件资源压力、晚期/资源失败不重跑、旧缓存恢复、跨段文本更新、首帧缺失时钟及失败的全局媒体进度、中文回退与 ASS 字形 alpha。

真实 CUDA 对照覆盖三套旧样式×普通/前导六组，每组含弹幕、醒目留言和礼物，全部通过。最大平均 RGB 差 0.382、最大改变像素比例 0.50%。这些结果仅覆盖旧样式的 ASS 纹理桥接，不准入其他 Scene 样式的逐对象 CUDA 图。

完整 8759.91 秒成片及 5060 Ti 实机性能仍待验证，当前保持自动长片暂停。Windows 修复测试包仍使用现有 0.8.4 版本号，不代表发布新版本；位于 `release/bili-record-2k-webui.zip` 和 `release/bili-record-2k-setup.exe`，未安装到远端、未推送或发布。

Windows 构建成功，最后受影响的四个测试文件共 33 项再次通过。构建产物已检查包含分段调度、字形验收、Fontconfig、自动长片暂停和 ASS 前导时钟修正；包内 FFmpeg SHA-256 与本轮回归使用的二进制一致。包内 h5-card 样片总显存采样峰值 7744 MiB，同样包含其他应用占用。

## 在 RTX 5060 Ti 上复验

在修复后的仓库目录运行，输出目录必须与源文件目录分开。每次运行使用新的输出目录，先 30 秒，再 300 秒，全部通过后才跑完整长片。

```powershell
$recordingSource = 'X:\哔哩录播2K\883263-真栗\20260925_205728-明天在重庆和平精英吃鸡节'
node scripts/desktop-burn-regression.cjs --input "$recordingSource\883263_真栗_20260925_211006.clean.mp4" --danmaku "$recordingSource\883263_真栗_20260925_211006.danmaku.jsonl" --output-dir '.tmp/desktop-burn-regression/5060ti-current-30' --duration 30 --style current
```

后两次分别改为 `--duration 300` 和 `--duration full`，并改用独立输出目录。三套旧样式可通过 `--style h5-card`、`bubble`、`minimal` 复验。也可通过 `--decoder software` 对照 CPU 解码，或 `--ffmpeg` 指定待测安装包中的 FFmpeg。

每次生成 `report.json`、`verification.json`、`result.mp4`、抽帧 PNG 和分段诊断；失败保留 `failure.json`。先检查 `ok`、实际设备/流水线、完成媒体时长、时长与时间戳健康，再看字形抽帧和性能。旧可用版本须在同一台设备、同一录像、同一编码参数、相近背景负载下对照，不能把本机 Laptop 结果当成 Ti 回归结果。
